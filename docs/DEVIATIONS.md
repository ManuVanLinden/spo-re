# Deviations from the original game's behaviour

This page lists every place where this build makes Spore behave differently from the same GOG executable on
Windows. **A change that can alter how the game behaves adds its row here**, with the reason, the effect a player
could notice, and the switch that turns it off if there is one. A reimplementation of a Windows API with the same
observable result is not a deviation; the design pages under `docs/design/` describe those.

**What stays unchanged.** No instruction of the game is edited. The translated C under `build/` is a mechanical
rendering of the whole executable, and the tree carries no patches to the game or to any library. The runtime
reads the game data (`Data/`, `DataEP1/`, `bp1content/`) unmodified from the GOG install and never writes it. The
one exception is opt-in: with `SPORE_SKIP_INTRO=1` the file layer serves one byte of the application properties
changed on read (2.14). Every deviation below lives in the environment the game runs in: the CPU model the
translator gives it, the Windows API layer, the graphics and audio back ends, and the window.

Tags: **[same as Windows]** means the observable result matches Windows though the mechanism differs;
**[differs]** means a player or the game's own logic could notice.

## 1. CPU and floating-point model (translator, `recomp/`)

| # | Deviation | Effect | Switch | Where |
|---|---|---|---|---|
| 1.1 | **NaN sign.** x86 produces the negative "real indefinite" NaN; arm64 produces a positive default NaN. Not reproduced. | [differs] Only code that inspects a NaN's sign bit would see it; no such code found. | none | translator.md |
| 1.2 | **x87 values are host doubles, never 80-bit.** The exe has no 80-bit memory operands and runs at 24-bit precision control, which the translator honours. | [same as Windows] for 24-bit and 53-bit results; rare last-bit differences remain for the ~1,400 double-precision operands. | none | translator.md; runtime-abi.md (x87) |
| 1.3 | **Denormals.** The game asks for flush-to-zero; arm64's FZ flushes inputs and outputs. An x87 store of a float-range denormal gives a denormal on x86, zero here. | [differs] Game arithmetic is unlikely to reach it. | none | hle-crt.md (control words) |
| 1.4 | **`fsin`/`fcos`/`fsincos`/`fptan` outside ±2^63** leave the operand and set C2, as the x87 does. | [same as Windows] | none | translator.md |
| 1.5 | **D3D9's FPU rule.** On Windows, `CreateDevice` without `FPU_PRESERVE` puts the x87 into 24-bit precision; the device applies the same control-word change to the translated x87 state at `CreateDevice` and `Reset`. | [same as Windows] | none | `runtime/d3d9null/src/d3d9_device.c` |
| 1.6 | **Memory ordering (policy p2).** x86 gives every plain load acquire and every plain store release ordering (TSO); arm64 does not. The translator lowers as acquire loads (`ldapr`) and release stores (`stlr`): the 388 sites of `data/threads/ordering-sites.json` (the ticket spinlock's spin loads, every access to the Dac thread's state globals, the thread stop flags, 296 candidate publication stores), every `.data`/`.tls`/`CONST` global access, and every heap access in the 296 functions directly reachable from a worker thread: 138,592 of 1,829,807 explicit accesses. `lock`/`xchg` stay sequentially consistent. Stack, read-only, `fs:` and all other heap accesses stay relaxed; a misaligned ordered access is a plain access plus a fence. | [differs, potentially] The known lock-free hand-offs have x86 ordering; a race the game gets away with on x86 through heap data outside those sets (job bodies, virtual callees, unlisted pointer publications) could still misbehave. No failure attributed to ordering yet. | `SG_MEMORDER=p0\|p1\|p2\|p3` (or `recomp/translate.py --memorder`) at translation time: p0 is the relaxed emission, p1 the listed sites only, p3 orders every non-stack access (x86-TSO for heap and global data) | memory-ordering.md; runtime-abi.md §3.4 |
| 1.7 | **Misaligned atomics.** A locked access that crosses a 16-byte boundary takes a process-wide spin lock that is not serialised against overlapping aligned atomics. On x86 the bus lock makes it atomic against everything. | [differs, potentially] Matters only if an aligned atomic also touches the same bytes. | none | runtime-abi.md §3 |
| 1.8 | **Thread priorities and affinity** are stored and reported back but do nothing; macOS has no affinity API. | [differs] Scheduling, not results. Havok's workers and the job manager run at the default QoS. | none | runtime-core.md |
